# 会议意图提取（正式校读版）

## 证据与校读方法

- 原始文件：《The whole conversation from the meeting (Jul 31).pdf》，27页，Google Docs导出；正文含中文 ASR 与自动英文翻译。
- 校读原则：以中文上下文为主，英文只作辅助；术语误识别按上下文解释，但不擅自恢复无法确认的词；页面中的指示性语言如“这里/这块”缺少白板画面时标为“指向不确定”。
- 页1–4、26–27噪声很大；页5–25包含主要项目讨论。以下引文保留原转写中的可读部分，并给出 PDF 页码。

## 1. 产品应用场景

| 原话/可靠转写 | 解释 | 置信度 |
|---|---|---|
| “家庭环境里，比如说桌面级的一些任务……拿水……物体的摆放……帮我把这个桌面去清理一下……丢一下垃圾。”（页5） | 主场景是家庭/个人桌面；取物、整理、垃圾处理是代表任务 | 高 |
| “后面再发展……不局限于……收拾桌面……厨房……后期也可以用在工厂里面。”（页10） | 厨房、咖啡/饮品与工厂是远期扩展，不是首阶段验收 | 高 |
| “如果是需要深度信息的话，你们的一个相机可能要换一下”（页21）；“先用着，后面再改”（页25） | 允许阶段性使用现有广角+深度组合，后续再换更合适传感器 | 高 |

**真实意图：** 先在可控桌面构造可重复、可测的真实物理任务，再证明框架可扩展；不应一开始就把“全屋整理/厨房/工厂”做成范围。

## 2. 老师认为的科研问题

1. **怎样把通用“脑子”变成高效可靠的物理 Agent。** “怎么去更好地利用这个脑子”“更好更快……效率……完成度要高”（页12–13）。
2. **怎样提供先验/中间变换，让模型选对并串好 Skill。** “怎么设计这个 prompt”“经过我们中间的一些变换……帮助他更好地找到这个 skill”（页9）；“不是一个检索……是一个 planning”（页15）。
3. **视觉何时介入。** 老师明确比较任务开始观察、动作结束后验证、执行中预判三种时机（页12）。
4. **失败后怎样理解状态并恢复。** “没有成功……换下一个 policy”“重新计划、重新规划”（页12）；“失败之后怎么根据失败的状态，然后再去调整”（页21）。
5. **怎样使贡献跨模型版本保持。** “它变成6.0之后，你的这个东西是不变的，也可以使用”（页19），即上层契约/方法应模型可替换，而不是只对某个 prompt/model 过拟合。

## 3. 老师提出的核心创新点（会议当时的设想）

| 会议设想 | 原话依据 | 调研后的校正 |
|---|---|---|
| Prompt/结构化先验使 Codex 更好地调 Skill | “怎么设计这个 prompt……更好地找到这个 skill”（页9） | Prompt 本身已被 ProgPrompt/RAI/OpenETA 等覆盖；只能作为 baseline，需提出可量化的 verifier/selection 方法 |
| 更快、更高完成度 | “又好又快……论文方面的重点”（页13）；“成功率……完成时间”（页18） | 仍可作为目标/指标，但“比无先验 prompt 快”基线太弱，必须加入 OpenETA/CaP-X/结构化工具等强基线 |
| 视觉介入与失败恢复 | “什么时候去介入……结束之后……还是中间预判”（页12）；“换下一个 policy……replan”（页12） | DoReMi、Code-as-Monitor、LERa、PLanAR 已覆盖一般概念；需收窄到证据门控、误判/成本与真实 handoff |
| Memory 加速相似任务 | “历史是做过类似的……很快地完成一个相似任务”（页17） | REFLECT、LRLL、ASPIRE、OpenETA 已覆盖；需研究可信晋升与适用域，不能直接写成创新 |
| 方法对模型升级稳定 | “换一个模型……上层几乎是不变的”（页19） | 有价值的设计要求；可实验做跨 Planner/模型稳健性，但不是架构首创 |

## 4. Skill、Codex/VLM、Prompt、Vision、Planning、Replanning 的关系

```text
用户指令
 → Codex/VLM：理解目标；结合 Prompt/结构化先验做 Planning（不是只做检索）
 → Skill Library：选择、参数化、串联已开发能力
 → Rule-based / ACT / Diffusion Policy 等 Policy 实现 Skill
 → Camera/Vision：开始时理解世界；结束时检查效果；必要时执行中监控
 → 若失败：重观测当前状态 → Retry / 换 Policy / Replanning
 → 完成用户目标；将经过验证的经验用于后续相似任务
```

原话依据：

- “不同的方式……rule base……ACT……diffusion policy……去学习 skill”（页6–7）。
- “Codex……找到对应的 skill 控制我的 bot……完成我的任务”（页7–8）。
- “Codex……或者 Vision language model……做一个 planning……调用不同的 skill……把不同 skill 串起来”（页8）。
- “不需要你……中途……编程……把这些 skill 给你”（页8–9）。
- “再 take picture……判断当前是什么状态……replan”（页11–12）。

**解释：** Skill 是已验证能力；Policy 是 Skill 的一种实现；Prompt/Schema 是 Planner 的先验；Vision 提供世界证据；Replanning 只在执行证据使当前计划不再适用时发生。老师并未要求 Codex 在运行时从零训练或自由生成控制代码，反而明确反对这种慢路径。

## 5. 优先实现的最小系统

老师的次序非常明确：

1. 列出候选 Skill，“先做出一小部分……把这一整套跑通……后面再慢慢填”（页13）。
2. “一开始我就只做 P and place……只做一种方式……rule base……先把它跑通”（页14）。
3. 跑通后才检查“有没有恢复功能”“时间上面有问题”“怎么设计 prompt”（页16）。
4. 视觉/纠错算法先做一个可测版本，“搞出来一个去测试，然后出什么问题再去解决”（页23）。
5. 真机/仿真选择上，会议倾向先处理物理识别；转写提到仿真到现实的负担（页23），但具体是否完全拒绝仿真仍属转写不确定。

因此最小系统是：**单一 rule-based Pick-and-Place + 当前相机/临时深度 + 开始/结束视觉证据 + 明确成功判定 + trace**。Codex、复杂 Prompt、Memory、多 Policy 与在线监控均是后加消融，不应成为第一个可运行依赖。

## 6. 评价指标

### 会议明确

- 任务成功率/完成度：页13、16、18。
- 完成时间/响应速度/效率：页9、13、16、18。
- 不同先验/Prompt 相比 baseline 的增益：页16–18。
- 失败后的恢复与最终完成用户目标：页11–12、16、21。

### 本轮调研建议补充

- false accept、false abort、UNKNOWN、恢复触发精度/召回；
- clean-start 与 chained-terminal-state 成功差；
- VLM calls/tokens、尾部时延、平均 retry/replan；
- 安全拒绝、越权调用、无新观测继续执行次数；
- 跨 Planner/model 版本的性能保持。

页16–18 中“五六小时、30分钟、10秒”等是老师解释 baseline 的**举例**，不是已测实验数据，不能写进结果。

## 7. 老师要求重点调研的内容

- 学术论文之外要亲自试模型/系统（页20）。
- 方向很新，关注小红书等社区上可能早于论文的技巧（页20）。
- Prompt/信息供给如何影响 Skill 调用、速度和成功率（页16–21）。
- Vision 的介入时机、身份跟踪、多模态判定与纠错（页12、21–23）。
- 失败状态、Policy 切换、Recovery/Replanning（页12、16、21）。
- 深度/鱼眼/多相机与能力边界（页1–4、21、24–25）。
- 找到强 baseline 并量化“怎么更快、成功率更高”（页16）。

## 8. 明确属于工作量、不能单独当创新的部分

会议转写中未找到老师清晰逐字说“这不是创新”的完整句子；不能伪造直接引语。但以下语义是明确的：Skill/平台等属于工作量或基础设施，论文 Contribution 在如何利用上层模型“又好又快”地控制与恢复。

- “大框架”中很多模块和平台可视化是工作量；核心是“怎么利用好这个脑子”（页12）。
- 列 Skill、实现 Skill、搭平台是先决条件（页10、13），不是老师最终强调的论文点。
- 页19 明确：“这些只是说是去丰富你的那个库的……你的贡献点在这和这。”由于白板指向缺失，**“这和这”的精确模块转写不确定**；但语义足以确认“丰富 Skill 库”不被老师视为核心贡献。
- 语音/Customer 接口主要是产品交互入口（页13–14），会议未把语音识别本身列为算法创新。
- “真机比较成功率和时间”是实验方式，不是方法创新。

## 9. 原文中暴露的现状问题

1. 当前纯像素偏移/鱼眼方案“不特别准”（页1–3）；鱼眼近200°，不能简单套普通针孔模型（页3）。
2. 深度信息缺失或范围有限；页24提到相机范围约0.3–3（单位未说，转写不确定）。
3. 当时没有正式测试成功率；“挺低”“二三十”语义可能指20–30%，但上下文噪声大，**不得作为确定数值**（页3）。
4. 同一物体可能因检测中断被识别为新物体，存在身份跟踪问题（页22）。
5. 视觉是否需要其他多模态模型、如何把结果反馈给 Planner 尚未决定（页22）。
6. 广角/深度相机并用、先用现有后换设备是暂定方向（页24–25）。

## 10. 仍需向老师确认

1. 白板上页19所指的两个 Contribution 精确是哪两个框/箭头？
2. “Codex”是特指 Codex 产品/模型，还是泛指 coding agent/LLM Planner？会议多处 ASR 为 code/code x/cods。
3. Prompt 优化是预期主算法，还是仅为对比；能否接受将主线转成 verifier routing/handoff benchmark？
4. “又好又快”的主目标如何排序：危险误放行、成功率、完成时间、调用成本各自权重？
5. 首个 Pick-and-Place 的对象、目标区域、初态分布、人工干预与成功判据。
6. 真实实验允许的次数、审批、安全协议、相机固定方式和深度有效范围单位。
7. Memory 是会话上下文、检索式经验、Skill 代码，还是三者；什么条件可晋升生产库？
8. 是否要求论文具备算法新意，还是接受真实系统/基准/数据集型 Contribution？
9. 页23对仿真的态度和“直接在物理里面做”的确切范围；是否仍需仿真 Baseline？
10. 页25“8月底到10月底”是否是项目周期；其前后语音噪声大，转写不确定。

## 11. 会议意图与调研结论的冲突

老师在页18–20推测企业界可能已有、学术界“应该没有那么快”，并强调抢时间。以 2026-08-06 的证据看，这一预期已经失效：OpenETA、PLanAR、Semantic Handoff、CaP-X、ASPIRE、ENPIRE、RHO 等已分别或整体覆盖会议设想。**应保留老师的实施顺序和产品逻辑，但必须更换论文创新表述及 baseline。**
