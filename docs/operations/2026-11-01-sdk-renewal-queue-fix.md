# SDK 延迟确认后的续期调度修复

## 问题与实际边界

双端抓包已证明公网设备通道存在重传，但尚未定位所有 renewal_failed 的内部异常。本轮先修复可独立复现的软件问题：设备续期确认尚未返回时，原 fresh 处理会等待同一个 Promise，期间的新鲜浏览器响应不会触发后续续期。确认晚到后又等待下一次 250ms 挑战周期，消耗原本已经很短的剩余租约时间。

新增 PostgreSQL 集成回归先在旧代码复现：在设备 ACK 延迟 850ms、期间有多次有效心跳的条件下，仅产生一次续期；预期的立即第二次续期断言失败。该证据证明调度遗漏，不等于证明它是全部现场故障的唯一原因。

## 行为与模块

- services/cloud-api/src/control/leases.js：每个持有者最多保存一个待处理新鲜事件，等待设备 ACK 期间不并发发送。ACK 返回后立即消费该事件，重新检查身份、浏览器新鲜度、设备上下文、只读准备状态与数据库租约；没有新事件则停止循环。
- 在异步身份、数据库和设备确认边界检查持有者是否仍有效，避免撤销后迟到的工作继续下发续期或恢复本地状态。
- 失败诊断只输出固定组件名、阶段、白名单错误码及最多60000ms的耗时。任意异常文本、用户/会话/设备标识、令牌、签名和载荷不进入日志；诊断回调失败不阻止撤销。
- services/cloud-api/src/device-runtime.js：将受限诊断写到现有业务服务 stderr/journal，不新增外部日志传输、配置或数据库表。
- tests/node/public_access/control-renewal-queue.test.js 与既有 control-fixture.js：覆盖延迟确认合并、500ms到期、撤销竞态、慢数据库、数据库租约过期和日志脱敏/回调失败。

这不是自动重新申请租约或重发运动命令。浏览器500ms、签名设备租约1000ms、数据库过期拒绝均不改变；没有修改角色、SDK初始化确认、设备readOnly门禁或运动授权。

## 验证

新增7项集成测试通过，使用本机隔离PostgreSQL与测试设备；旧代码的主要延迟场景断言先失败、修复后通过。原租约/心跳/SDK权限11项组合回归通过（包含当时新增的前3项）。完整公网访问回归352/352通过、零跳过；包括真实本机WebSocket和Python模拟worker。首轮351通过、1项因测试读取PYTHON而非EDGE_TEST_PYTHON、未指定已有虚拟环境而超时；补齐两者指向同一已有环境后完整回归通过，未修改该worker或延长其测试期限。

测试均不连接真实SDK。本轮尚未部署，未执行新的电机使能、闭爪、运动；10分钟真机状态验收仍待上线后独立验证。真实网络若持续延迟超过原有期限，仍会按原规则断开。

## 数据、资源与运行

无数据库迁移、权限变更、资源文件、新依赖、端口或Ubuntu改动。沿用现有Node24、PostgreSQL、staging业务服务与部署启动方法。仅云端两份现有源码需要更新；已有相机任务未提交改动不进入固定包。

部署应固定源码提交与包摘要，核对线上清单，零租约/零在途命令后备份、切换并仅重启业务API。回退到原发布，不涉及数据库回滚。先验收无SDK初始化的授权续期，再按已有批准范围显式连接与只读状态采集；不自动重试连接，不放宽超时。
