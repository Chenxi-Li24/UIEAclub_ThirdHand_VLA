# 双相机角色化在线部署设计

日期：2026-08-05  
项目：ThirdHand / TH-Fanxy 视觉感知  
状态：总体分工已确认，规格自检完成，待用户书面复核

## 1. 决策摘要

当前使用两台物理相机完成一套逻辑 RGB-D 感知：

- **Lumos 鱼眼 RGB 是唯一主视觉坐标系**，负责大视野搜索、实例分割、目标选择、持续身份和遮挡/离场后的重识别。
- **Intel RealSense D435 是度量深度源**，负责距离、点云、三维位置和抓取前几何验证。
- D435 RGB 只用于标定、诊断和健康检查，不接替 Lumos 决定“目标是谁”。
- D435 深度通过经过独立验证的外参和时间门禁注册到 Lumos 原生像素；Lumos 实例掩码选择目标点云。
- 在线接近采用“走—停—看—再走”的分段闭环。每个观测点都必须重新确认同一目标身份和新鲜三维位置。

算法实际运行在 Ubuntu/RTX 5060 上，物理相机只提供图像和深度流。“部署到相机”在本文中指将对应相机流接入持续运行的在线感知服务，而不是修改相机固件。

未来更换为带深度的鱼眼相机时，仍保留“主视觉 RGB + 度量深度”两个逻辑角色；两者改由同一设备提供。上层检测、身份、三维目标状态、安全门禁和机械臂接口不随设备型号变化。

## 2. 目标与非目标

### 2.1 本次目标

1. 将已通过 GPU 冒烟测试的 RTMDet-Ins + DINO 身份链路接入 Lumos 实时 RGB。
2. 将 D435 实时深度按时间、标定和坐标约定注册到 Lumos 图像。
3. 生成持续、可审计的目标状态：实例 ID、掩码、三维位置、不确定度、时间戳、标定 ID 和可操作状态。
4. 在只读页面显示两路相机、检测/身份结果、深度覆盖和所有阻断原因。
5. 保持 `robot_execution_enabled: false`；在线部署只产生 Dry Run 感知结果，不发送机械臂、夹爪或 CAN 指令。
6. 用稳定接口兼容未来单台深度鱼眼相机。

### 2.2 本次非目标

- 不解锁真实抓取或自动运动。
- 不把通用 COCO 权重冒烟通过解释为透明瓶任务模型验收通过。
- 不绕过 Lumos 曝光、任务模型、双相机外参或手眼标定失败。
- 不依靠降低检测阈值来掩盖任务模型召回不足。
- 不同时运行两套相互独立的目标身份系统，也不在接近阶段切换主 RGB 坐标系。
- 不提前为尚未选型的未来深度鱼眼编写厂商专用 SDK 代码。

## 3. 方案比较

### 3.1 采用：Lumos 主视觉 + D435 深度注册

Lumos 从搜索到接近始终维护目标掩码和身份；D435 只为该掩码提供度量深度。这避免身份交接，并且与未来单机 RGB-D 鱼眼的逻辑接口一致。

### 3.2 不采用：搜索用 Lumos、抓取时完全切换到 D435 RGB-D

该方案直观，但会在最危险的接近阶段引入图像坐标切换、目标 ID 交接、视场变化和额外外参误差。D435 RGB 视场较小，也不应成为现有 Lumos 数据训练出来的身份模型的隐式替代输入。

### 3.3 暂不采用：两台相机独立检测后投票

独立检测可以提供冗余，但需要两套训练分布、身份合并和冲突仲裁。当前主要瓶颈是任务数据、曝光和标定，不是缺少第二套分类投票；此方案增加复杂度而不能消除三维标定风险。

## 4. 逻辑角色与设备映射

上层模块只能依赖逻辑角色，不得把 `Lumos` 或 `D435` 型号散落到算法判断中。

| 逻辑角色 | 当前设备 | 未来设备 |
|---|---|---|
| `canonical_rgb` | Lumos RGB | 深度鱼眼 RGB |
| `metric_depth` | D435 Depth | 深度鱼眼原生 Depth |
| `debug_rgb` | D435 RGB | 可选的设备调试流 |
| `fusion_mode` | `cross_camera` | `native_aligned` 或设备原生注册 |

配置表达角色映射，例如：

```yaml
camera_roles:
  canonical_rgb: lumos_rgb
  metric_depth: d435_depth
  debug_rgb: d435_rgb
  fusion_mode: cross_camera
```

未来只替换设备适配和标定配置：

```yaml
camera_roles:
  canonical_rgb: fisheye_rgbd_rgb
  metric_depth: fisheye_rgbd_depth
  debug_rgb: null
  fusion_mode: native_aligned
```

## 5. 组件边界

### 5.1 相机采集适配器

分别拥有 Lumos 和 D435 的采集生命周期，输出带单调时间戳、帧序号、尺寸和健康状态的不可变帧。采集层不做目标识别，也不生成机械臂坐标。

### 5.2 时间配对器

以 Lumos RGB 为主时钟，为每个接受的 RGB 帧选择时间最接近的 D435 深度帧。当前过渡硬件的初始门限为：RGB-depth 配对时差不超过 50 ms、融合帧龄不超过 200 ms、机器人只读位姿与融合时刻相差不超过 50 ms。帧重复、时间倒退或任一门限超出时，不生成可操作 RGB-D 观测。这些门限可以在验收后收紧；放宽必须重新形成硬件测量证据和书面验收，不能作为解决掉帧的临时手段。

没有合格深度时，Lumos 仍可维持可见身份，但目标状态必须是“仅可跟踪、不可抓取”。

### 5.3 主视觉模型管线

只读取 `canonical_rgb`：

1. RTMDet-Ins 输出类别、置信度和 Lumos 原生像素实例掩码。
2. DINO 在实例掩码内生成身份描述符。
3. 身份内存维护稳定实例 ID、遮挡状态、重入确认和歧义拒绝。

模型管线不直接读取 D435 RGB，不因为 D435 检测结果改变目标身份。

### 5.4 深度注册与三维定位

在当前 `cross_camera` 模式下：

1. 将 D435 Z-depth 反投影到 D435 光学坐标。
2. 使用经过审核的 `T_lumos_from_d435` 变换到 Lumos 坐标。
3. 使用 Lumos SEUCM 模型投影到 Lumos 原生像素并执行 z-buffer。
4. 使用 Lumos 目标掩码选择前景点云，剔除边缘、稀疏点和离群点。
5. 通过经过审核的相机到机器人变换生成基座坐标位置和保守协方差。

在未来 `native_aligned` 模式下，只替换前 3 步的深度提供器；掩码点云、目标状态和安全门禁不变。

### 5.5 双相机融合器

融合器接收身份观测、注册深度、相机健康状态、机器人只读位姿和标定审核结果，输出统一目标状态。状态至少包含：

- 稳定实例 ID 和类别；
- Lumos 原生像素掩码；
- 目标在机器人基座坐标的三维位置；
- 位置协方差或等价不确定度；
- RGB/深度/机器人位姿时间戳；
- 相机模型、外参和手眼标定内容哈希；
- `trackable`、`actionable` 和明确阻断原因。

### 5.6 在线服务和页面

在线服务持续运行上述感知管线，并通过只读 API/页面提供：

- Lumos 主画面及实例掩码、类别、ID；
- D435 RGB 调试画面和深度健康状态；
- 掩码内有效深度覆盖、三维位置和不确定度；
- 时间配对、曝光、模型、标定和机器人执行锁状态；
- 每个目标不可操作的确切原因。

页面不得提交客户端三维坐标作为可信抓取目标；服务端只接受自己生成并仍然新鲜的目标状态。部署阶段继续拒绝所有抓取授权。

## 6. 分阶段数据流

### 6.1 搜索

Lumos 大视野检测所有候选并维护身份。D435 可以提供粗略深度健康信息，但没有 Lumos 掩码的 D435 点不得创建任务目标。

### 6.2 锁定与定位

任务选择一个稳定 Lumos 实例 ID。系统以其掩码筛选注册深度，只有深度覆盖、点数、时间差、标定 ID 和不确定度全部合格时，才产生可操作三维位置。

### 6.3 分段接近

未来接入运动后，机械臂每移动一段必须停稳并重新观测：

1. Lumos 确认目标仍是同一稳定 ID；
2. D435 提供新鲜且有效的三维位置；
3. 机器人只读位姿与图像时间匹配；
4. 所有安全门通过后，规划器才可计算下一小段运动。

本次部署只验证该状态机产生的 Dry Run 决策，不执行运动。

### 6.4 近距离与深度失效

D435 接近最小工作距离、透明/反光目标或边缘时可能失去有效深度。发生这种情况：

- 目标可以继续保持可见身份；
- 当前三维状态立即变为不可操作；
- 不使用跳变深度，也不无限期复用旧坐标；
- 未来抓取阶段只能从最后一个仍在时效门内的可信预抓取位姿，执行另行验收的短距离受限接近，并结合夹爪/接触反馈；该动作不属于本次部署范围。

## 7. 失败处理与安全约束

系统默认 fail-closed：

| 情况 | 行为 |
|---|---|
| Lumos 不可用或曝光不合格 | 不创建/更新可操作目标 |
| D435 深度不可用 | 允许身份跟踪，禁止三维抓取 |
| RGB/深度时间差超限 | 拒绝本次融合 |
| 身份歧义或重入尚未确认 | 保持 tentative/ambiguous，禁止抓取 |
| 标定缺失、方向错误、内容哈希不匹配或未独立验证 | 禁止输出可操作基座坐标 |
| 点云稀疏、边缘污染或不确定度超限 | 禁止抓取 |
| 客户端提交自定义三维坐标 | 服务端拒绝 |
| `robot_execution_enabled: false` | 所有运动授权拒绝 |

当前验收报告中的 Lumos 低曝光、任务检测器未接受透明瓶、双相机/手眼标定未验证等阻断原因必须原样保留。在线管线成功运行不等于抓取任务完成。

## 8. 验收设计

### 8.1 自动测试

- 相机角色配置不能把 D435 RGB 设为默认主视觉。
- 时间配对覆盖正常、超时、重复、倒退和单路掉线。
- 深度注册覆盖坐标方向、z-buffer、无效深度、掩码边缘和标定 ID。
- 身份覆盖遮挡、长间隔重入、同类实例、低质量观测和歧义拒绝。
- 在线服务覆盖模型异常、CUDA 异常、相机重连、客户端坐标伪造和执行硬锁。
- 同一录制输入重复回放必须得到确定性一致结果。

### 8.2 真实硬件 Dry Run

至少连续运行 30 分钟并记录：

- 两路帧率、帧龄、配对时差和掉帧/重连；
- Lumos 曝光与检测结果；
- 每个目标的 ID 连续性、深度覆盖、三维抖动和阻断原因；
- GPU p50/p95 延迟和显存；
- 页面显示与服务端状态一致；
- 机械臂、夹爪和 CAN 无写入。

运行期间还必须满足：

- 在线工作进程无未捕获异常、无持续增长的帧队列；处理跟不上时丢弃旧帧并保留最新帧；
- 模型 p95 延迟不超过 300 ms，GPU reserved 峰值不超过 7.2 GiB；
- 任一路超过 2 s 没有新帧时，API 和页面必须在同一状态周期内显示 stale/disconnected，恢复后重新经过时间与身份确认门禁；
- 机械臂、夹爪和 CAN 写操作计数为零。

场景至少包含单物体、多同类物体、遮挡、离场重入、目标移动、透明瓶、深度丢失、单相机掉线和过期帧。

### 8.3 完成标准

本次“算法部署到对应相机”只有同时满足以下条件才算完成：

1. Lumos 实时流持续运行主视觉模型与身份内存，而非只做单帧脚本冒烟。
2. D435 实时深度持续注册到 Lumos 掩码，并输出带不确定度和标定来源的三维状态。
3. 在线 API/页面能显示结果和阻断原因，掉线后安全重连。
4. 自动测试、录制回放和真实硬件 Dry Run 均通过。
5. 执行硬锁保持关闭，并有证据证明未发送机械臂运动。

任务专用透明瓶召回、标定和抓取闭环仍使用各自门禁验收；若这些门禁失败，在线部署可以完成，但目标必须显示为不可操作，不能宣称“抓取完成”。

## 9. 实施顺序

1. 把物理设备映射改为逻辑相机角色，并补角色契约测试。
2. 建立 Lumos/D435 带时间戳采集与配对边界。
3. 将现有 RTMDet、DINO、身份和深度注册模块接入在线工作进程。
4. 将统一目标状态通过只读 API 接入测试页面。
5. 完成录制回放、失败注入和真实 30 分钟 Dry Run。
6. 保留所有阻断门禁，发布只读在线感知；不解锁机械臂。

## 10. 未来深度鱼眼交接

未来相机接入时新增一个设备适配器，输出同一份 `canonical_rgb`、`metric_depth`、时间戳、相机模型和健康状态契约。随后：

1. 重新标定新鱼眼内参及相机到机械臂的手眼变换；
2. 验证或使用厂商提供的 RGB-depth 原生对齐，并保留独立验收；
3. 用新鱼眼图像微调和验收检测模型；
4. 将 `fusion_mode` 切换为 `native_aligned`；
5. 复跑同一套身份、三维、安全、回放和硬件 Dry Run 验收。

不保留当前 D435-to-Lumos 外参和跨相机时间配对层；其他上层模块不因换相机重写。
